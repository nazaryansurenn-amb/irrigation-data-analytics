# Local SQL Analytics Workspace

This project is a local/offline SQL Server analytics workspace built with Python,
Streamlit, pandas, pyodbc, local Qwen through LM Studio, and ChromaDB RAG.

It is designed for hands-on data analytics learning with a real SQL Server
database while keeping data local.

## Core Pieces In Simple Words

- **SQL Server**: the local database source. The app reads data only and does not
  modify SQL Server.
- **Streamlit**: the browser interface for selecting databases, tables,
  questions, charts, and AI tools.
- **pandas**: the Python data layer. It turns SQL results into dataframes for
  previews, KPIs, checks, charts, and exports.
- **Local Qwen**: the offline AI model running through LM Studio. It explains
  tables, drafts read-only SQL, and summarizes results.
- **RAG / ChromaDB**: the local knowledge base. It searches documents from
  `knowledge_base/` and gives relevant context to Qwen.
- **AI Agents**: specialist prompts for profiling, SQL analysis, data modeling,
  anomaly checks, BI planning, and validation.
- **Power BI Outputs**: local CSV and helper files that can be opened in Power BI
  Desktop for report practice.

## Main Capabilities

- Explore local SQL Server databases and tables.
- Load read-only table samples into pandas.
- Profile columns, missing values, duplicate rows, and basic KPIs.
- Build Streamlit charts.
- Ask local Qwen questions about selected SQL tables.
- Run safe read-only SQL generated by Qwen.
- Use local ChromaDB RAG knowledge files from `knowledge_base/`.
- Export Power BI-ready CSV files for BI practice.
- Run local AI specialist agents for profiling, SQL, operations analytics, Power BI, RAG, and validation training.
- Save local agent task memory and SQL Server context memory for future agent runs.

## Agent Memory Center

The app includes an **Agent Memory Center**.

It has two types of local memory:

- **Agent task memory**: saves solved agent questions, selected table, generated SQL,
  SQL execution summaries, final answers, timestamps, and report paths.
- **SQL Server context memory**: scans all local SQL Server user databases read-only
  and stores metadata only: database names, table names, columns, data types,
  estimated row counts, key-like columns, and detected business concepts.

Memory files are saved locally in:

```text
outputs/agent_memory/
```

Typical generated files:

- `agent_task_history.jsonl`
- `latest_agent_task.json`
- `sql_server_context.json`
- `sql_server_context.md`

The context scan does **not** store raw table rows. It is designed to help agents
understand the database landscape while keeping data local and private.

SQL Server context memory search is concept-aware. Agents are instructed not to
look only for exact command words. For example, a command about "paying users"
can search wider across payment, collection, service user, water user,
contract, identifier, `Kod`, WUA, and operational segment concepts.

The Memory Center also includes a **Global Agent Command Center**. This lets you
ask agents questions without first selecting or loading a database table. The
global agents use SQL Server context memory, remembered tasks, optional RAG
context, and safe read-only SQL execution from a `master` connection.

The default global mode is **Auto Coordinator (choose needed agents)**. In this
mode Python routes the command to the needed specialists, such as Senior
Analytics Lead, SQL Analyst, Data Model / Join Discovery, Anomaly Detection,
Operations Analytics, Power BI, Data Profiler, RAG Knowledge, and Validator. The Coordinator
then combines their reports, selects the best SQL drafts, and produces the final
answer.

Executable global SQL should use fully qualified names such as:

```sql
SELECT COUNT(*) FROM [Structure_2025].[dbo].[Payment];
```

## AI Agent Workspace

The app includes an **AI Agent Workspace** that runs local Qwen with specialist
agent prompts. Agents do not modify SQL Server data and do not execute arbitrary
Python. They produce local reports and optional SQL drafts for review. When the
safe execution checkbox is enabled, Streamlit validates agent SQL as read-only,
runs it through Python, shows the result, and asks Qwen to produce a final answer
from the actual SQL output.

Available agents:

- **Senior Analytics Lead Agent**: frames business questions, defines KPIs, segments, hypotheses, and executive meaning.
- **Data Profiler Agent**: explains table structure, data quality, missingness, and duplicates.
- **Data Model / Join Discovery Agent**: infers likely table relationships, join paths, grain, and model risks.
- **SQL Analyst Agent**: writes safe read-only SQL Server query drafts.
- **Anomaly Detection Agent**: proposes outlier, mismatch, duplicate behavior, and trend-break checks.
- **Operations Analytics Agent**: interprets irrigation/WUA data using KPI, service usage, collection, data quality, and anomaly thinking.
- **Power BI Agent**: recommends dashboard pages, visuals, DAX, and report story.
- **RAG Knowledge Agent**: connects local retrieved documents to the current analysis.
- **Validator Agent**: checks for unsafe SQL, invented columns, weak assumptions, and logic gaps.
- **Full Agent Review**: combines the specialist perspectives into one final report.

The workspace also includes an **Agent Team Review** button. This runs several
specialists one by one, then asks a Coordinator Agent to combine their findings
into one practical action plan. This is useful for interview demonstrations
because it shows a realistic agent workflow:

1. Senior Analytics Lead frames the question, metrics, and executive meaning.
2. Data profiler checks structure and quality.
3. Data Model / Join Discovery agent suggests relationship and grain checks.
4. SQL analyst proposes read-only SQL Server drafts.
5. Anomaly Detection agent suggests outlier and mismatch checks.
6. Operations Analytics agent translates the data into operational BI thinking.
7. Power BI analyst recommends report pages, visuals, and DAX.
8. Validator checks assumptions and safety.
9. Coordinator produces the final combined plan.

Agent reports are saved locally in:

```text
outputs/agent_reports/
```

Typical generated files:

- `agent_full_report.md`
- `data_profiler_report.md`
- `sql_analyst_report.md`
- `sql_agent_queries.sql`
- `operations_analytics_report.md`
- `powerbi_agent_recommendations.md`
- `rag_knowledge_report.md`
- `validator_report.md`
- `agent_team_report.md`
- `agent_team_summary.json`
- `agent_team_sql_drafts.sql`
- `agent_run_manifest.json`

Timestamped history copies are saved in:

```text
outputs/agent_reports/history/
```

The app also shows a SQL safety check for generated agent SQL drafts. Agent SQL
execution is capped and read-only, and works when one exact table is selected or
the same schema.table is selected across multiple databases.

## Optional Operational BI Training Layer

The project keeps an optional advanced BI export layer for Power BI practice.
It is hidden by default so the main demo stays focused on the local SQL AI
assistant, agent workflow, and RAG knowledge base.

This optional layer treats the irrigation/WUA system as operational analytics:

- Water users = service users.
- WUA = organization unit or segment.
- Water delivered = service usage.
- Payment collected = payment collection.
- Unpaid amount / debt = unpaid service amount.
- Missing passport, phone, or address = data quality issue.
- Abnormal water delivery with low payment = operational anomaly.

The section can generate these CSV files:

- `outputs/powerbi/clean_table_export.csv`
- `outputs/powerbi/kpi_summary.csv`
- `outputs/powerbi/data_quality_summary.csv`
- `outputs/powerbi/risk_training_summary.csv`

These files are meant for easy Power BI Desktop practice.

The optional BI training layer supports these source modes:

- **One database table**: export one table from one database.
- **Multiple exact tables**: select several exact tables from one or more
  databases and export one combined training dataset.
- **Same schema.table across multiple databases**: select several databases,
  choose one shared table such as `dbo.Payment`, and export one combined dataset.

When multiple databases or tables are selected, the app adds:

- `SourceDatabase`
- `SourceTable`

These columns are useful in Power BI as slicers, legends, or comparison fields.
For unrelated table structures, the CSV export is the safest path because pandas
can combine different columns while preserving missing fields.

## Power BI Automation Pack

After generating the CSV outputs, click **Generate Power BI Automation Pack**
inside the Streamlit app.

The app creates additional local helper files:

- `outputs/powerbi/measures.dax`
- `outputs/powerbi/power_query_import_scripts.m`
- `outputs/powerbi/sql_views_for_powerbi.sql`
- `outputs/powerbi/dashboard_blueprint.md`
- `outputs/powerbi/data_dictionary.csv`
- `outputs/powerbi/risk_kpi_definitions.csv`
- `outputs/powerbi/manifest.json`

These files help automate the BI preparation workflow:

- `measures.dax` contains ready-to-copy DAX measures.
- `power_query_import_scripts.m` contains Power Query M import templates.
- `sql_views_for_powerbi.sql` contains optional SQL Server view scripts for manual review.
- `dashboard_blueprint.md` explains the recommended report pages and visuals.
- `data_dictionary.csv` documents columns, missingness, and suggested BI roles.
- `risk_kpi_definitions.csv` is a legacy file name that now stores operational
  BI KPI definitions and recommended visuals.
- `manifest.json` records when the pack was generated and which table it was built from.

The app does not publish reports to Power BI Service. Everything is generated
locally and can be reviewed before being used in Power BI Desktop.

## Connecting Power BI Desktop To SQL Server

Power BI can connect directly to SQL Server:

1. Open Power BI Desktop.
2. Select **Get Data**.
3. Choose **SQL Server**.
4. Enter the server name, for example `localhost`.
5. Choose the database.
6. Select **Import** for a simple local demo, or **DirectQuery** for live querying.
7. Choose the tables you want to analyze.
8. Click **Load** or **Transform Data**.

For this learning demo, exported CSVs are also provided for simple Power BI
practice.

## Importing Exported CSV Files Into Power BI

1. In the Streamlit app, use the optional advanced BI training layer if it is enabled.
2. Select a database and table.
3. Click **Generate Power BI-ready BI outputs**.
4. In Power BI Desktop, choose **Get Data -> Text/CSV**.
5. Import the CSV files from `outputs/powerbi/`.
6. Build relationships and visuals as needed.

## Example DAX Measures

```text
Total Records = COUNTROWS(clean_table_export)

Missing Values = SUM(data_quality_summary[MissingValues])

Average Missing Rate = AVERAGE(data_quality_summary[MissingRatePct])

High Missing Columns =
COUNTROWS(
    FILTER(data_quality_summary, data_quality_summary[MissingRatePct] >= 30)
)
```

## Example SQL Query

```sql
SELECT
    DATEFROMPARTS(YEAR([PaymentDate]), MONTH([PaymentDate]), 1) AS PaymentMonth,
    SUM(CAST([PaymentMoney] AS float)) AS TotalPayments
FROM [dbo].[Payment]
WHERE [PaymentDate] IS NOT NULL
  AND [PaymentMoney] IS NOT NULL
GROUP BY DATEFROMPARTS(YEAR([PaymentDate]), MONTH([PaymentDate]), 1)
ORDER BY PaymentMonth;
```

## Local / Offline Design

The project is designed to run locally:

- SQL Server stays local.
- Streamlit runs locally.
- Qwen runs locally through LM Studio.
- ChromaDB stores embeddings locally in `chroma_db/`.
- Power BI CSV exports are written locally to `outputs/powerbi/`.

The app does not modify SQL Server data. SQL usage is read-only.
